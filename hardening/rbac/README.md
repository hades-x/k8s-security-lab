# Least privilege
lab-viewer: read workloads, Services, events and logs; no Secrets/exec. lab-dev: dev/staging Role only; workload changes but no Secrets API, exec, RBAC, namespaces or impersonation. soc-analyst: logs/events/workload/report metadata; bind namespace-by-namespace, no global binding by default. Example bindings target lab-viewers/lab-developers/soc-analysts groups in dev and staging only.
IMPORTANT: ability to create workloads is not a guarantee against indirect secret access. A developer may mount namespace Secrets or use a more privileged SA unless additional admission policy restricts secret mounts and serviceAccountName. Keep sensitive Secrets and privileged SAs out of dev/staging; this preparation does not claim to close that escalation path. Logs may contain application secrets.
audit-secrets.sh captures kubectl auth can-i --list for the current caller, all RBAC objects, a static secret-reader inventory (wildcards/resourceNames included), and concrete user/SA SAR checks. Group memberships, external webhook authorizers and future aggregated roles need separate review; can-i --list is not an exhaustive inventory of every identity. Run before and after and retain full JSON for traceability.
